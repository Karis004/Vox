## 本轮实机定位与无需刷固件的排查

本机识别Arduino Leonardo为COM10。只读USB串口先后捕获两轮基础AT超时；正式采集文件中，香港2026-10-18 14:09:35发送AT，14:09:38等待超时并报告SYNC FAIL；保存时间08:00，CLOCK仍等待首次校时。该轮**ESP基础串口命令没有得到回应，尚未进入Wi-Fi／TCP／服务器请求阶段**。这缩小到ESP供电／EN／UART／运行状态范围，不证明芯片损坏，也不能只凭外观接线没变排除接触或供电问题。服务器同期没有带log1标识的主板请求，与此现象一致。

新闻则是独立故障：服务器中news／actuarial的AI阶段返回HTTP522；查询现有AI供应商模型列表又出现ReadTimeout。天气和文本成功。只能确认当前上游不可用，不能以今天的证据断言之前四五天每次都是同一原因；本轮没有更换供应商、模型或密钥。

在项目Codex终端（已验证的PowerShell7环境）运行：

```powershell
./scripts/capture-device.ps1 -Port COM10 -Seconds 90
```

关闭Arduino串口监视器，使用实际Arduino端口；脚本监听115200、不发送串口命令、不上传／重启固件。监听期间可以按实体8号或等30秒自动重试。默认写到Git忽略的 `data/diagnostics/device-时间-编号.jsonl`。脚本退出会释放串口；它只是需要排查时用的临时工具，不是常驻服务。Windows PowerShell5在本机阻止了脚本运行，本轮没有修改系统执行策略；使用已经可运行的项目Codex终端即可。

采集器只保留命令类别、阶段、结果、状态码、数字和电脑采集时间；不保存Wi-Fi名称／密码、HTTP正文、API密钥或任意原始行。已有串口文本可用 `-ReplayPath 路径` 转为同格式。没有相应标记的旧固件无法凭空恢复没有输出的内部细节。

发布新网页后：右上角设备日志→**导入USB日志**→选择JSONL→按采集时的香港日期查看。导入可分批且去重，重复导入不会生成重复事件；保留期限仍30天。文件最大2MB／10000事件，每批最多500；服务器拒绝未知字段、无时区时间、超过30天／未来超过5分钟的时间。来源明确标为USB采集，不冒充服务器接收到的网络请求；采集时间依赖电脑时钟，没有读到的阶段不能推定成功。当前无鉴权原型不提供日志真实性认证。

面板分别展示**最近带固件标识的请求、服务器校时响应、USB记录的设备校时结果、最近设备故障**。可按校时／网络与HTTP／新闻与AI／USB筛选。每次device请求新增开始和结束事件，以request_id及响应X-Vox-Request-ID关联；开始没有结束可能是请求处理中／进程中断，不代表设备已收到。

新闻事件分为每个固定来源请求、材料筛选、AI整理／纠正、整稿结果。来源名／HTTP状态／耗时／条数和安全故障摘要可直接查，原始上游错误正文仍只在原模块测试里查看。**检查AI（少量调用）**会对现有配置发一个小请求，记录成功／失败及建议，不自动调用或切换供应商。部分模块失败的稿件五分钟后允许重新生成；正在播放的旧快照仍保留到原三小时期限，健康稿仍可正常复用。

当前实机优先做的检查（无需改线或刷固件）：将整套设备的两路USB都断开数秒再重新接通，复测是否仍停在AT。如果仍失败，断电后只检查以下已有线路；不要把ESP供电改成5V，也不要改变成功供电方案。

| 从哪里 | 接到哪里／核查内容 |
| --- | --- |
| AMS1117 OUT | ESP 3V3，确认实际3.3V供电，灯亮本身不证明电压稳定 |
| 3.3V分线节点 | ESP EN，确认未松动 |
| 公共GND节点 | ESP GND，确认共地 |
| ESP TX | Leonardo D0/RX1 |
| Leonardo D1/TX1 | 已有电平转换板B0 |
| 电平转换板A0 | ESP RX |

若灯也不亮先查供电；灯亮且AT持续无回应，重点检查上述串口路径、ESP运行状态／保存波特率。当前程序只在115200通信；仅凭USB日志不能测出ESP实际波特率或电压，不自动认定Wi-Fi密码错误。串口恢复AT回应后再继续看Wi-Fi→TCP→HTTP→时间解析；无需重做新闻配置。

## 查看日志

网站右上角“设备日志”图标打开独立窗口，不改变三栏编排。按**香港日期**查询、手动刷新、加载更早记录；点击当天稿件查看完整文本及实际分段，点“导出当天”下载JSON。日志启用前的历史无法补录。

记录保存在配置数据库旁的 `device-log.db`，默认本机 `data/device-log.db`、Docker `/app/data/device-log.db`，沿用现有vox-data卷。普通重建保留，不需要新增.env变量或密钥。最近30天、最多10000条事件／200份稿件；先到期限或数量上限的记录会清理。日志数据库故障不应阻止设备校时／取稿，服务器终端会显示不含私密正文的故障类型。

| 记录 | 能看什么 |
| --- | --- |
| 服务器启动／停止 | 服务生命周期；强制终止不保证留下停止事件 |
| `/device/time` | 请求状态、服务处理耗时、主板上报时间、时差、设定时间、下一次香港播报／校时 |
| 晨报准备／模块结果／成功／失败 | 启用模块数、生成耗时、各模块成功／警告／失败及上游HTTP状态码或安全错误类型 |
| `/device/briefing` | 等待503、就绪200、稿件id、分段数、手动或定时触发（新固件） |
| `/device/briefing-part` | 稿件id、段号、状态、响应字节、服务处理耗时；新固件还上报上一帧和取稿耗时 |
| `/device/event` | 新固件在最后一段估算等待结束后，尽力发送一次“帧已发送”报告 |
| 稿件存档 | 实际用于设备的正文、每段文本／字节／字符数／估算等待、模块结果和配置hash |

不保存请求头、任意query、完整配置、API密钥或原始上游错误正文。**稿件本身仍可能是私人内容**；当前网站沿用原有无鉴权原型，日志和导出与现有配置页一样需要部署环境保护，不要公开分享数据库或导出文件。

事件表示**服务器收到请求**，不是设备一定收到响应。HTTP200不证明喇叭出声；`finished`只表示主板报告全部帧已发送且估算等待结束，不是TTS完成回执。完全断网、主板掉电和未到服务器的请求无法记入服务器。发现日志缺口时，结合设备串口检查。

## 字段与排查顺序

事件展开后可查看安全JSON字段；以下时间单位为毫秒：

| 字段 | 含义 |
| --- | --- |
| `duration_ms` | 服务器处理本次HTTP请求／生成模块的耗时，不含完整香港往返、ESP AT准备或后续日志写入 |
| `fetch_ms` | 新固件上一次完整取稿事务耗时，含AT／TCP／接收／关闭；下一次请求上报，最后一次在finished上报 |
| `sent`、`sent_ms` | 上一段零起始段号、发完TTS帧的主板millis；millis不是北京时间，约49天回绕，重启归零 |
| `wait_ms` | 发完上一帧后预留的估算播放等待；不是测得音频长度 |
| `preload` | 1表示请求下一段时，当前段仍在估算播放窗口内 |
| `reason` | 新固件校时原因boot／reset／save／hourly |
| `trigger`、`event` | 手动button／定时daily；event为主板任务epoch，并非精确出声时间 |

1. 选问题当天，查看是否有校时请求，状态是否200、设定时间和时差是否合理。
2. 查晨报生成是否失败或只有部分模块失败；上游401／429等状态可提示密钥／额度问题。详细来源错误仍到原网页模块测试查看，不把私密上游响应写进长久日志。
3. 找同一个稿件id，看段号是否完整，是否出现503／410或重复请求；410后可能从头重播。
4. 打开稿件，确认“祝你一天愉快”是否恰好在下一段开头。如果停顿发生在两段之间，优先看估算等待和取稿。
5. 若 `duration_ms` 很短、`fetch_ms` 很长，更像ESP准备／网络往返；若取稿提前完成仍静音，优先检查过长的估算等待。固件串口 `[PART SEND]` 另记录 `frame_interval_ms`，表示两次发送帧的间隔。
6. 同一帧内部也停顿、日志分段位置对不上时，才进一步查语音模块、标点处理、供电及温度；现有软件日志不能替代音频听测或电气测量。

读取接口：`GET /api/device-logs?day=YYYY-MM-DD&before=事件id&limit=100`；`GET /api/device-logs/briefings/稿件id`；`GET /api/device-logs/export?day=YYYY-MM-DD`。均不缓存，按保存期限查询。

## 为什么当前程序可能停顿

每帧最多180 UTF-8字节，约60个纯中文字符。现有程序在发完一帧后等待 **字符数×450ms＋1500ms**。例如60个中文字符会等约28.5秒；如果模块实际更早读完，剩余时间就是静音。然后旧程序才执行AT准备、建TCP、取下一段，额外增加网络停顿。长稿分段更多，自然有更多这样的边界；尾声也可能被切入最后一段。

这是代码中可以确认的机制，和用户描述相符，**尚不是实机逐段测量后的最终定论**。目前没有证据表明HS-S77-PL在固定句子前因过热强制暂停。也没有可靠的厂家资料证明其TX返回哪些完成状态；不能套用其他型号协议。

本次固件在当前段播放窗口内提前取下一段，复用原192字节缓冲；上一帧估算结束后直接发已取到的下一帧。时间校正延后到本轮晨报结束，语音提示覆盖缓冲时会取消预取并重新取同一段。失败仍重试同一段，复位会清掉预取。**没有减短未经实测的450ms估算**，避免后一段提前发出截断前一段，所以不能承诺停顿全消失。

当前 `SoftwareSerial(5,6)` 仅用D6发送。Leonardo的D5不支持SoftwareSerial接收，不能直接把语音TX接D5就期待完成反馈；D8～D11又用于按钮。将来取得HS-S77-PL厂家TX协议后，需要另选兼容引脚并核对电平，才可改用真实完成状态。见 [Arduino SoftwareSerial官方限制](https://docs.arduino.cc/learn/built-in-libraries/software-serial)。

## 更自然的声音：两条选择

| 选择 | 适用目标 | 实际改动 |
| --- | --- | --- |
| **优先：服务器生成自然TTS音频＋ESP32-S3音频板** | 更自然、中英文、同时减少散板和接线 | 服务端增加音频生成／缓存接口，设备改成下载并播放音频；需要迁移固件，不是替换UART模块即可 |
| DFRobot Gravity DFR0760 V2 | 尽量沿用现有主控，先改善中英文支持 | 官方有UART／I2C及内置喇叭，需要改协议；先听样音，离线合成仍不保证接近真人 |

建议候选 [Waveshare ESP32-S3-AUDIO-Board](https://docs.waveshare.com/ESP32-S3-AUDIO-Board)：集成Wi-Fi、音频编解码／功放、喇叭接口、TF、RTC，并支持Arduino／ESP-IDF。可采用“每天生成一次音频、缓存、先下载完整文件再播放”的简单设计，补听复用音频，按实际播放进度判断结束。这样设备负责播放，声音主要由服务端TTS决定。外接八键矩阵仍需核对可用GPIO／扩展引脚，不能假定直接套用Leonardo接线。

声音服务可先试听 [Azure Speech中文神经语音](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/language-support?tabs=tts)，例如Xiaoxiao／Yunxi的新闻播报风格。沿用已有AI供应商时先确认它是否提供音频TTS；现有聊天模型API密钥不等于已经支持音频。费用及音色效果另行确认，本次未开通或实现新音频服务。

[DFRobot DFR0760官方资料](https://wiki.dfrobot.com/dfr0760/)确认中英文、UART／I2C、内置喇叭；这些功能不证明它比当前板自然。优先用包含AIA、PRU、HSBC、中文和数字的同一段稿试听，再决定购买，避免只根据“AI语音”商品名换板。

## 先把现有板子固定成一整件

建议先不重做已成功的电路：**所有板固定在一块绝缘底板，再把整块底板固定到墙或带通风孔的项目盒**。搬动时拿底板，避免拉线。

1. 用尼龙隔离柱＋螺丝固定有安装孔的板；孔径实测后选M2.5／M3。没有孔的板用夹持支架或3D打印卡座，喇叭单独固定。不要把板背面焊点贴到金属，也不要用热胶盖住稳压器／芯片。可参考 [Adafruit隔离柱安装](https://learn.adafruit.com/neotrellis-soundboard/install-standoffs)。
2. 按“主控／ESP”“供电”“语音／喇叭”“按钮”分区，板固定后再换合适长度的线。每根关键线两端贴同一标签，例如L2→D8、TTS RX→D6；保留接线照片和逐根表。
3. 用扎带座固定线束和USB进线，让受力落在底板而不是杜邦插头；插接处留少量检修余量，不用扎带勒元件。按钮外露方便按，喇叭留出声孔，稳压板周围通风。
4. 稳定后把经常松动的供电分线移到洞洞板／合适端子，或改成带锁扣的JST线束；购买时核对间距、极性、引脚定义和电流，不把所有接头都换掉。参考 [Adafruit接线指南](https://learn.adafruit.com/wires-and-connections?view=all)。
5. 整理前断开两路USB。保留现有成功供电关系：**两路5V正极分开、GND共地**；不要为了少一根线随意合并电源。整理完先做白天短测；安装整齐不等于完成电气安全验证。

第一阶段只需绝缘底板、合适隔离柱／夹座、扎带座、标签和短线；盒子尺寸等布局固定后再买，避免一次买一堆不合适的配件。
